# Testing Rules

See `Modules/Tests/AGENTS.md` for detailed async testing patterns and mock examples.

## Behavior checks

When adding, changing, or reviewing a test:

1. Name the behavior and the regression that must make the test fail. Exercise the real implementation through its public interface.
2. Use expected values from a requirement, a worked example, or an independent fixture. Do not repeat the production calculation to derive the expectation.
3. Keep domain logic in production code. Use doubles at API, hardware, clock, or persistence boundaries. Verify visible outcomes and boundary request data.
4. Make assertions run. Require expected errors and callbacks, establish a nonempty starting state for filtering tests, and wait for observable async completion.
5. Check that a no-op or broken behavior would fail. Replace or remove assignment-only, property-count, duplicate, and mock-calculation tests. Check existing real coverage before removal and record any remaining gap.

## Framework
- **Prefer Swift Testing** (`@Test`, `#expect()`) for new test files
- When adding tests to an existing XCTest class, follow that class's framework and patterns
- Use XCTest helpers from the `TestKit` module when needed

## Naming
Use snake_case: `test_<operation>_when_<condition>_then_<expected_result>()`

When referring to a property or class name, keep its original casing within the snake_case method:
```swift
func test_loadOrders_when_error_occurs_then_shows_error_state()
func test_evolvePokemon_when_passed_a_Pikachu_then_it_returns_Raichu()
```

## Structure
Organize every test into three blocks with comments:
```swift
// Given
// When
// Then
```

## Test Data
- Use `.fake()` factory methods from the Fakes module for model instances
- Use `.copy(property: newValue)` to create modified copies of immutable models
- Create static factory methods or private extensions for custom test data builders

## Mocks
- Hand-written mocks, never generated by third-party mocking frameworks
- Naming: `Mock<ServiceName>` (e.g., `MockOrderService`, `MockAnalyticsProvider`)
- Place mocks in `Mocks/` subdirectories within test targets
- Mock structure: configuration properties, spy properties for verification, stub return values

## Test Locations
- Main app tests: `WooCommerce/WooCommerceTests/`
- Module tests: `Modules/Tests/<ModuleName>Tests/`
- Test plan: `WooCommerce/WooCommerceTests/UnitTests.xctestplan`

## Async Tests
- Mark `async` XCTest methods with `@MainActor` to prevent flaky failures from threading issues
- This applies to all `async` test methods in XCTest classes (Swift Testing handles this differently)

## Core Data in Tests
- Use `storageManager.performAndSave({ storage in ... }, completion: {}, on: .main)` for all storage insertions and mutations
- Do NOT use `storage.insertNewObject(...)` directly — always go through `performAndSave` to ensure thread-safe operations
- This prevents flaky test failures caused by Core Data threading violations

## What to Test
- **ViewModels**: state changes, action dispatching, data transformation, error handling
- **Stores**: action handling with MockNetwork and MockStorageManager
- **Remotes**: request building and response mapping with MockNetwork
- **Mappers**: JSON parsing with fixture files
