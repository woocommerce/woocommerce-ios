# Mobile Status Report field reference

The Mobile Status Report (MSR) is generated by the WooCommerce iOS app and attached to every support ticket, both as
the Zendesk custom field `51884914117268` and as `mobile_status_report.txt`. It is the app-level counterpart to the
server-side WooCommerce System Status Report (SSR), which carries no device or app information and is empty on
tickets filed from the login screen.

The same report is shown to merchants under **Settings → Help & Support → Mobile status report**, with copy and
share actions. That row is always visible, including when no store is selected: the report needs no store and no
network, and on the login screen it is the only device information a ticket would carry.

## Reading the report

Every section heading states whose values it describes:

| Scope | Meaning |
| --- | --- |
| `(app-wide)` | Covers the whole app on this device, whichever store is selected. |
| `(selected store: <url>)` | Covers only the named store — the one the app had selected when the ticket was filed. |
| `(no store selected)` | The app had no store selected, so the section has nothing to report. |

The distinction matters for merchants with more than one store: an `(app-wide)` value cannot explain a problem
that happens on one store and not another, and a store-scoped value says nothing about the merchant's other
stores.

Three conventions apply throughout:

- **The report never touches the network.** Every value is read from `UserDefaults`, Core Data, the app's own
  in-memory caches, or a system API. This is a stronger guarantee than the report strictly needs, and it is
  deliberate: it keeps ticket creation off the critical path entirely and lets the Help & Support screen render
  the report instantly, logged out and with no store selected. Adding a network read to any section would
  silently give that up — do not add one.
- **A failed lookup never fails the report.** A section that throws is replaced by `Info not found`. Ticket
  creation must never be blocked, so every section is best-effort.
- **Absent values say why they are absent.** `not set`, `never`, `not evaluated` and `unknown` are followed by a
  reason wherever one exists, because each is the expected state in some configurations and a fault in others.

Several values are snapshots of an in-memory cache rather than persisted state, and read `not evaluated in this
session` when the app has not yet had cause to compute them. That is a meaningful answer in itself — it says the
merchant has not visited the relevant screen since launching the app — and it is called out per field below.

## App `(app-wide)`

| Field | Meaning | Values |
| --- | --- | --- |
| `Version` | Marketing version with the build number in brackets. | e.g. `21.3 (2103003)` |
| `Build` | Which build configuration the app is running. | `appStore`, `alpha` (internal distribution), `localDeveloper` |

`alpha` is worth noticing on its own: internal builds can carry changes that are not in the released app.
