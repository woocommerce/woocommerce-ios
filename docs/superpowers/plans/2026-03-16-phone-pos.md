# Phone POS Implementation Plan

> **For agentic workers:** REQUIRED: Use superpowers:subagent-driven-development (if subagents available) or superpowers:executing-plans to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Adapt the WooCommerce POS to work on iPhones in portrait, with full feature parity alongside the existing iPad landscape layout.

**Architecture:** A new `POSPhoneRootView` provides the phone layout (tab bar + cart sheet), while `PointOfSaleDashboardView` remains the iPad layout. `PointOfSaleEntryPointView` branches between them based on `horizontalSizeClass`. Navigation state is lifted into an `@Observable` `POSNavigationModel` so it survives size-class transitions. A new `.pointOfSalePhone` feature flag gates the phone layout.

**Tech Stack:** SwiftUI, Swift Testing, `@Observable`, custom `PresentationDetent`, POS design tokens

**Spec:** `docs/superpowers/specs/2026-03-16-phone-pos-design.md`

```swift
import Foundation

@Observable
@MainActor
final class POSNavigationModel {

    enum Tab: Hashable {
        case sale
        case orders
        case bookings
        case settings
    }

    var selectedTab: Tab = .sale
    var isShowingCheckout: Bool = false

    // Secondary feature presentation state.
    // On iPad these drive full-screen covers from the floating menu.
    // On phone these map to tab selection.
    // Both read and write must work so SwiftUI bindings can dismiss covers.
    var isShowingOrders: Bool = false {
        didSet { if isShowingOrders { selectedTab = .orders } }
    }
    var isShowingBookings: Bool = false {
        didSet { if isShowingBookings { selectedTab = .bookings } }
    }
    var isShowingSettings: Bool = false {
        didSet { if isShowingSettings { selectedTab = .settings } }
    }

    func showCheckout() {
        isShowingCheckout = true
    }

    func dismissCheckout() {
        isShowingCheckout = false
    }

    /// Called after payment success — dismisses checkout and returns to the sale tab.
    func startNewOrder() {
        isShowingCheckout = false
        isShowingOrders = false
        isShowingBookings = false
        isShowingSettings = false
        selectedTab = .sale
    }
}
```

```swift
                POSSettingsView(settingsController: posModel.settingsController)

        static let orders = NSLocalizedString(
```

**Critical — Checkout button behavior on phone vs iPad:**
On iPad, the checkout button calls `posModel.checkOut()` which transitions to `.finalizing` stage AND starts the payment flow (syncs order + activates payment model). On phone, the checkout button in the cart sheet should only navigate to the checkout screen — it should NOT auto-start the payment flow.

Read `PointOfSaleAggregateModel.checkOut()` to understand what it does. For the phone flow, the cart sheet's checkout button should:
1. Call `posModel.checkOut()` to sync the order and transition `orderStage` to `.finalizing`
2. Call `navigationModel.showCheckout()` to present the checkout screen
3. But the payment model should NOT auto-activate — the user must explicitly tap "Tap to Pay" or "Cash Payment"

If `checkOut()` auto-starts payment, you may need to add a parameter or a separate method (e.g., `syncOrderForCheckout()`) that syncs without activating payment. Alternatively, the phone checkout view can observe `paymentModel` state and simply not display the inline payment UI — letting it run idle until the user taps a payment button.
