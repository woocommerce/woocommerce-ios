1. Building Stage — Catalog + Cart

Decision: Persistent cart bar with pull-up sheet

Reasoning: Merchants need to see cart changes as they tap items. A bottom bar showing ~1.5 rows of cart items provides visual feedback (items animate in), while maximizing catalog browsing space. The sheet can be expanded for full cart management.

Product list: Rows, not a grid — matching the current iPad layout. Long product names and variations display more effectively in rows.

2. Checkout Screen

Decision: Pushed screen with cart review, prominent total, two stacked payment buttons

Reasoning: The checkout screen is the final confirmation before payment. Cart contents and grand total are the priority — no reader status or connection UI. On phone, the primary card method is Tap to Pay (system UI takeover). Two simple buttons: "Tap to Pay" (primary) and "Cash Payment" (secondary), stacked vertically.

3. Payment Result States

Decision: Full-screen takeover for processing, success, and error — same as iPad

Reasoning: These states already work well at any screen size. They're simple centered layouts with an icon, message, and action buttons. No adaptation needed.

4. Tab Bar Navigation & Secondary Features

Decision: Bottom tab bar with four tabs: Sale | Orders | Bookings | Settings

Reasoning: The iPad's floating control menu doesn't work on phone. A tab bar gives direct access to all feature areas. The tab bar is hidden during checkout and payment (full-screen push). Orders and Bookings use their existing compact layouts. "Exit Point of Sale" lives in Settings.

5. Platform & Rollout

  • Phone orientation: Portrait only — no landscape support
  • iPad: No changes — existing landscape layout remains as-is
  • Feature flag: Phone POS behind a feature flag for gradual rollout
  • Existing compact layouts: Orders, Bookings, and Settings already adapt to compact size class — no redesign needed
